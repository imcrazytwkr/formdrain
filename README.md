# FormDrain

A headless form submission ingresser with optional data validation and
notification systems. Currently uses SQLite as a storage layer (necessary for
persisting response data and reading form configuration).

Currently available notification channels:

- Email (via [Brevo](https://www.brevo.com))
- Discord (via [webhooks](https://support.discord.com/hc/en-us/articles/228383668-Intro-to-Webhooks))

## Getting Started

These instructions will get you a copy of the project up and running on your
local machine for development and testing purposes. See deployment for notes
on how to deploy the project on a live system.

### Prerequisites

Requires Go v1.26 or newer. The code in this repo and its dependencies are
100% Go with no CGo requirement.

### Building

Build process is automated using
[make](https://en.wikipedia.org/wiki/Make_(software)).
Assuming you already have `make` installed on your system, you can build
`formdrain` using it:

```sh
$ git clone 'https://github.com/imcrazytwkr/forkdrain'
$ cd feedhub

# Build using make
$ make build

# Alternatively, you can manually generate code and build directly
$ go generate ./routes/apiv1/api/...
$ go build -o formdrain .
```

## Running

FormDrain ships as a single binary generated by `make build` invocation and
does not require any external dependencies. However, it does require a
database file and minimal prior configuration in TOML format.

### Database

As mentioned in the preface, SQLite is the only currently supported storage
layer at the moment. To prepare a database file, apply migrations from the
`migrations/` directory to a DB file in order:

```sh
find migrations -type f -name '*.sql' | sort -n | while read -r migration; do
    sqlite3 /path/to/file.db < "$migration"
done
```

After migrations have done running, you should set `DBURL` env variable to
`sqlite:/path/to/file.db`. It can be a relative path but I would recommend
you only use absolute paths there so as not to leave a gap for undefined
behaviour.

### Configuration

The only **required** piece of configuration is the **notifiers** section:
you must set Discord username and name and email for Brevo notifier. These
are marked required as they are branding-related and FormDrain has been
designed to be as invisible as possible.

```toml
[notifiers.discord]
username = "FormDrain"
# avatar_url = ""

[notifiers.brevo]
sender_name = "FormDrain"
sender_email = "noreply@example.com"
```

The other fields are completely optional and if you would like to configure
them before running, see the supplied
[example configuration](config.toml.example).

## Usage

Currently this app provides the bare minimum of UI: only form response
ingesting and listing has been properly implemented. There is also an
`/auth/login` handle that sets an auth cookie. UI is left to the service
administrator to implement and deploy. The app is designed to sit behind an
API gateway/reverse-proxy that also serves the UI so a simple cookie-based
session is utilised for the API to minimise the required boilerplate to get
started.

### Site and Form Configuration

To configure a form, first add, in this order, a **user** that will be the
site owner, **site** configuration (captcha secrets), and the **form**
configuration itself. Refer to the following subsections that explain the DB
schema and provide the example queries.

#### Users

Users are stored in the `accounts` table.

| Column | Required | Notes |
| --- | --- | --- |
| `email` | Yes | Login identifier. Unique, case-insensitive. |
| `password_hash` | Yes | Argon2id in PHC format. Login will not accept a plaintext password here. |
| `created_at` | Yes | RFC 3339 UTC timestamp (for example `2026-08-14T13:00:00Z`). SQLite `datetime('now')` is not RFC 3339 and will fail when the row is read. |

Registration is currently not supported but I may add it later (pull requests
are welcome). To add a user, you must insert it manually.

`password_hash` must match what `HashPassword` in `services/account`
produces: Argon2id, time 6, memory 64 MiB, parallelism 1, 16-byte salt,
32-byte key. The stored value looks like
`$argon2id$v=19$m=65536,t=6,p=1$...`. You can use the following snippet to
quickly hash the password in the correct way:

```go
package main

import (
    "fmt"
    "os"

    "github.com/imcrazytwkr/formdrain/services/account"
)

func main() {
    hash, err := account.HashPassword(os.Args[1])
    if err != nil {
        fmt.Fprintln(os.Stderr, err)
        os.Exit(1)
    }

    fmt.Println(hash)
}
```

After writing it somewhere within this repo (e.g. in `cmd/hash_password.go`),
run it to get the compatible password hash:

```sh
go run ./cmd/hash_password.go 'your-password'
```

Hint: don't put it in the repo root to avoid collisions with existing "main"
package.

```sql
INSERT INTO accounts (email, password_hash, created_at)
VALUES (
  'admin@example.com',
  '$argon2id$v=19$m=65536,t=6,p=1$<salt>$<hash>',
  '2026-08-14T13:00:00Z'
);
```

#### Sites

| Column | Required | Notes |
| --- | --- | --- |
| `hostname` | Yes | Domain (FQDN) of the page that posts the form. Used for CORS and spam filtration. |
| `owner_id` | Yes | `accounts.id`. That account can list the site and its forms via `/api/v1`. |
| `hcaptcha_secret` | If the form uses hCaptcha | Server-side secret. |
| `recaptcha_secret` | If the form uses reCAPTCHA | Server-side secret. |

```sql
INSERT INTO sites (hostname, owner_id, hcaptcha_secret)
VALUES ('example.com', 1, 'your-hcaptcha-secret');
```

#### Forms

| Column | Required | Notes |
| --- | --- | --- |
| `site_id` | Yes | Parent site. |
| `captcha_type` | Yes | `hcaptcha` or `recaptcha`. Other values fail when the form is loaded. |
| `captcha_field` | No | Form field that holds the captcha token. Defaults to `h-captcha` or `g-recaptcha`. The token is stripped before storage. |
| `redirect_to` | No | If set, a successful POST returns HTTP 303 to this URL. Otherwise, HTTP 200. |
| `field_schema` | Yes | JSON object (must be `json_valid`). Declares which fields are stored. |
| `schema_version` | Yes | Copied onto each stored response. Keep it in sync with `field_schema.version` when you change the schema. |
| `notifiers` | Yes | JSON object (must be `json_valid`). Use `{}` if you do not want Discord or email. |

`field_schema` shape:

```json
{
  "version": 1,
  "fields": [
    {
      "name": "email",
      "type": "string",
      "required": true
    },
    {
      "name": "message",
      "type": "string",
      "required": false
    },
    {
      "name": "topics",
      "type": "array",
      "required": false,
      "items": {
        "type": "string"
      }
    }
  ]
}
```

Field `type` is `string`, `number`, `boolean`, or `array`. Arrays need
`items.type` of `string` or `number`. Unknown submitted keys are rejected
from form responses and only schema fields are persisted.

`notifiers` may include `discord`, `brevo`, both, or neither. Templates are
Mustache against the validated payload. Partials, `{{{`, `{{&`, and delimiter
changes (`{{=`) are rejected.

```json
{
  "discord": {
    "webhooks": [
      {
        "snowflake": "123456789012345678",
        "token": "webhook-token"
      }
    ],
    "title": "New submission",
    "template": "From {{email}}\n{{message}}"
  },
  "brevo": {
    "subject": "Contact form",
    "recipients": [
      {
        "email": "inbox@example.com",
        "name": "Inbox"
      }
    ],
    "template": "From {{email}}\n{{message}}"
  }
}
```

Discord `webhooks` are snowflake plus token (not a full webhook URL).
Optional Discord fields: `author` (`name`, `url`, `icon_url`), `url`,
`color`. Brevo requires `recipients` and `subject`. Notification failures do
not roll back the stored response.

```sql
INSERT INTO forms (
  site_id,
  captcha_type,
  captcha_field,
  redirect_to,
  field_schema,
  schema_version,
  notifiers
) VALUES (
  1,
  'hcaptcha',
  NULL,
  'https://example.com/thanks',
  '{"version":1,"fields":[{"name":"email","type":"string","required":true},{"name":"message","type":"string","required":false}]}',
  1,
  '{"discord":null,"brevo":null}'
);
```

### Submitting Forms

Point the HTML form at `POST /form/{id}`, or send JSON with a
`Content-Type: application/json` header. Include the captcha token under
the `captcha_field` form configuration property, or the default name for that
provider. The default names are also listed in each provider's documentation;
for completeness they are:

- `h-captcha` for hCaptcha
- `g-recaptcha` for Google reCAPTCHA

### Form Response Listing

> :information_source: **Refer to the OpenAPI specification for API details**
>
> While this section is provided here for "quick start" purposes, it is not
> intended to be a comprehensive guide. Since API handlers are generated
> from OpenAPI, the [specification](api/openapi.yaml) should be considered
> the single source of truth.

`GET /api/v1/forms/{id}/responses` returns a page of stored submissions for
a form. The form's site must be owned by the account in the
`formdrain_session` cookie (set by `POST /auth/login`).

Default listing is "newest first" (`created_at` descending, `id` ascending
as a tie-breaker). Pass `next_cursor` from the previous page as `cursor`
to fetch the next page. Do not mix a cursor with a different `sort` (sort
column) or `order` (sort direction).

| Query | Required | Notes |
| --- | --- | --- |
| `limit` | No | Page size. Default 50. Values above 100 are capped at 100. |
| `cursor` | No | Opaque token from `next_cursor`. |
| `sort` | No | Name of a schema field of type `string`, `number`, or `boolean`. Arrays are not sortable. |
| `order` | No | `asc` (default when `sort` is set) or `desc`. Invalid without `sort`. |

When `sort` is set, missing/unset values for that field sort last.

Each item includes `id` (UUID), `form_id`, `created_at`, `schema_version`,
optional `client_ip`, and `payload` (schema fields only). The last page
omits `next_cursor`.
